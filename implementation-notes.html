3. 設計決定（規格含糊處的選擇）

DECISION DC-01：Line Pay Cancel 將 paymentStatus 更新為 payment_failed

規格說「將 paymentStatus 更新為 payment_failed 或維持 unpaid，依實作策略決定」。

選擇 payment_failed，因為 unpaid 無法區分「尚未進入付款流程」與 「進入後取消」，payment_failed 讓前端能顯示「重新付款或取消訂單」的清晰選項。

DECISION DC-02：Token 儲存策略採 localStorage（MVP 路線）

規格允許 localStorage 或 httpOnly cookie。採用 localStorage 以降低初期複雜度， 不需要 CSRF 保護或 cookie 域設定，方便本機 / Vercel / Render 多環境切換。

Refresh Token 已於 2026-05-19 實作（見 Q-06），但同樣儲存於 localStorage。 兩個 token 共存於 localStorage 代表 XSS 仍可同時竊取兩者，Refresh Token 的安全效益相較 httpOnly cookie 方案有所折扣。詳見 T-06。

DECISION DC-03：會員訂單也要求填寫取餐手機號碼

規格的 guestInfo 說「會員訂單可保存取餐手機，用於訂單追蹤與取餐核對」（可選）。 實作上在結帳表單對會員也必填手機，理由：

  • 取餐叫號或簡訊通知需要手機
  • 訂單追蹤頁（/orders/guest）的「我的近期訂單」區塊顯示手機號碼，若為空則顯示「會員訂單未留手機」

DECISION DC-04：Staff 訂單管理頁「今日彙總」端點路徑

規格 API 路徑寫 GET /api/orders/summary/today， Express router 掛載在 /api/orders， 實際路由為 router.get('/summary/today', ...)， 完整路徑即 GET /api/orders/summary/today，與規格一致。

（注意：Swagger 文件有對外暴露此路由）

DECISION DC-05：手機版導覽採右側抽屜，點擊連結後自動關閉

規格要求「手機抽屜選單點擊導覽連結、登出或路由切換後應自動關閉」。 實作在 router.afterEach hook 自動將 isMenuOpen 設為 false， 確保直接修改 URL 也能關閉選單。

DECISION DC-06：Guest orderLookupCode 格式為 8 碼大寫英數

規格未規定格式，只要求 unique。 實作使用 nanoid 產生 8 碼大寫英數字串（e.g., A1B2C3D4）， 易於人工輸入、不易猜測，且符合 unique sparse index 要求。

DECISION DC-07：Guest token 有效期 7 天

規格說「建議 7 天」，採用此建議值。guestTokenExpiresAt = now + 7d。

DECISION DC-08：Refresh Token 有效期 30 天，token rotation

規格說「Refresh Token 可作為未來擴充」，未規定有效期與 rotation 策略。選擇：

  • 有效期 30 天（REFRESH_TOKEN_EXPIRES_DAYS，可透過環境變數調整）：平衡使用者便利性與安全性。
  • Token rotation：每次 POST /api/auth/refresh 成功後，舊 token 立即作廢、發放新 token。一旦 token 被盜用且對方先刷新，原使用者的下一次請求將因 401 自動 logout，降低無限延長攻擊視窗的風險。
  • DB 只存 SHA-256 hash：raw token 僅在 response 中出現一次，後端無法反推原始值。

4. 折衷考量

TRADEOFF T-01：MongoMemoryServer 整合測試 vs Mock DB

選擇： 所有後端 Jest 測試使用真實 MongoDB（in-memory），不 mock。

優點： 測試可捕捉真實查詢、索引行為與 Mongoose schema 驗證。 此類測試曾發現 mock 測試無法發現的 migration 問題。

代價： 測試必須 --runInBand（共用 MongoMemoryServer）， 並行執行會造成 port 衝突與 state 污染。

TRADEOFF T-02：前端 E2E 使用 page.route() mock 攔截，不起真實後端

選擇： Playwright 測試在 CI 不起真實 Node 後端，完全透過 mock interceptor 回應。

優點： CI 快速穩定，不需要 MongoDB 或 Line Pay sandbox， 可測試前端所有分支行為（包含錯誤狀態）。

代價： 無法測試真實 API contract；需要另外依賴後端 Jest 測試確保後端正確性。 每次後端回應格式異動（如 D-01、D-02）都必須同步更新所有 mock fixture。

TRADEOFF T-03：點數計算（原子更新 vs 應用層加減）

選擇： 使用 MongoDB $inc 原子操作更新 User.points。

優點： 防止並發 confirm 重複加點（對同一張訂單 confirm 兩次不會重複入帳）。 pointsEarned 欄位作為冪等鎖，只在值為 0 時才執行 $inc。

代價： 需要 $inc + $set 的複合更新，略增複雜度。

TRADEOFF T-04：Sales Report 時區處理集中在後端

選擇： 前端只送 YYYY-MM-DD 字串，後端統一轉換為台北時間（UTC+8）邊界。

優點： 前端不需處理時區，也不會因使用者瀏覽器時區不同而出現偏差。

代價： 後端需維護 getTaipeiDayRange()， 若未來需支援多時區則需重構。

TRADEOFF T-05：點數歷史資料來源（後端 API vs 前端 computed）

原始做法： PointsView.vue 從 orderStore.myOrders 過濾衍生，不額外呼叫後端。

現行做法： 新增 GET /api/points/history 端點，後端查詢所有有點數異動的訂單並回傳（見 D-03）。

改動原因： 前端 computed 受分頁上限制約（8 筆/次），若歷史訂單超過此上限，舊點數紀錄需手動「載入更多」才顯示，體驗不佳且不完整。

代價： 多一個 API 端點需維護；每次進入點數頁會發一次額外請求。

TRADEOFF T-06：Refresh Token 儲存於 localStorage vs httpOnly cookie

現行做法： Access Token 與 Refresh Token 皆儲存於 localStorage。

替代方案： Refresh Token 存入 httpOnly cookie，Access Token 仍放 localStorage（或記憶體）。httpOnly cookie 對 JavaScript 不可讀，XSS 攻擊無法直接竊取 Refresh Token。

選擇 localStorage 的理由：

  • Vercel + Render 跨域部署下，cookie 的 SameSite、Secure、Domain 設定較複雜，需配合 CORS credentials: true，初期容易出錯。
  • 本地開發環境（http://localhost）的 Secure cookie 有限制。
  • 兩種 token 都在 localStorage 時，Token rotation 仍可限制攻擊視窗：若 Refresh Token 被盜用後對方先刷新，原使用者下次請求將收到 401 並被自動 logout。

代價： XSS 仍可同時竊取兩個 token，Refresh Token 相較 httpOnly cookie 方案安全性較低。 若日後有更嚴格的安全需求，遷移路徑為：後端 POST /api/auth/refresh 改以 httpOnly cookie 設定 Refresh Token，前端移除 localStorage 中的 refreshToken 欄位。

✓ RESOLVED T-07：statusHistory（狀態歷史紀錄）— 已實作

規格說「建議新增狀態歷史紀錄（可選）」。已於 2026-05-19 實作：

  • order.model.ts — 新增 statusHistoryEntrySchema（status、changedBy ObjectId、changedAt Date），掛在 orderSchema 的 statusHistory 欄位（預設空陣列）
  • order.service.ts — updateOrderStatus() 每次狀態變更時 push 一筆 entry，記錄執行者的 userId

此欄位可作為後台稽核軌跡，前端 UI 若需顯示可直接讀取訂單回應中的 statusHistory 陣列。

5. 規格外的防禦性實作

功能說明
helmet() 設定安全 HTTP headers（X-Content-Type-Options, CSP 等）。規格未提及，標準 Express 安全實踐。
Rate limiting 全 API：200 req/min；Auth 路由：20 req/15min。使用 express-rate-limit，測試環境自動跳過（skip: () => env.nodeEnv === 'test'）。
